# Model Design — el_restrict_journal

## 1. Model: res.users (extension)

### Purpose
Adds a `journal_ids` Many2many field to `res.users`. This field lists the journals the user is **NOT allowed to use** for create/write operations. Empty list = unrestricted user (default).

### Field: journal_ids
- **Type:** Many2many → account.journal
- **Relation table:** `el_restrict_journal_users_rel` (auto-generated by Odoo)
- **String:** "Restricted Journals"
- **Help:** "Journals this user is NOT allowed to create or modify entries in. Leave empty for unrestricted users."
- **Groups:** `el_restrict_journal.group_restrict_journal_manager` (only managers can edit)
- **Computed:** No
- **Stored:** Yes (Many2many is always stored)
- **Index:** No (not used as a search key at the DB level; only via `user.journal_ids.ids` in record rules)

### Why this design
- **Many2many (not One2many):** A journal can be restricted for many users; a user can have many restricted journals → M2M cardinality.
- **On res.users (not a separate model):** Avoids the overhead of a new model + access rights + views. Uses the existing user form as the configuration point.
- **Empty = unrestricted:** Means default Odoo behavior is preserved when the module is installed but not configured. Admin users (with no journals in their list) are NEVER restricted.

### Groups on the field
```python
journal_ids = fields.Many2many(
    'account.journal',
    string='Restricted Journals',
    help='Journals this user is NOT allowed to create or modify entries in. '
         'Leave empty for unrestricted users.',
    groups='el_restrict_journal.group_restrict_journal_manager',
)
```

## 2. Model: account.move (extension)

### Purpose
Block create/write when the journal_id is in the user's restricted list. This is the **second layer of defense** (the first layer is the record rule on account.journal itself).

### Method: `create(vals_list)` (override)
```python
@api.model_create_multi
def create(self, vals_list):
    records = super().create(vals_list)
    restricted = self.env.user.journal_ids
    if restricted:
        for rec in records:
            if rec.journal_id in restricted:
                raise ValidationError(_(
                    "You are not allowed to create entries in journal '%s'."
                ) % rec.journal_id.display_name)
    return records
```

**Why post-super check?** Because `journal_id` may be set by `account.move.post()` or other server-side logic; checking after `super().create()` ensures the final state of the record is verified.

### Method: `write(vals)` (override)
```python
def write(self, vals):
    res = super().write(vals)
    restricted = self.env.user.journal_ids
    if restricted and 'journal_id' not in vals:
        # journal_id unchanged — check if any existing record is in restricted list
        # (this can happen if admin adds a journal to a user's restricted list AFTER
        # the user already has a record in that journal — we don't block reads, only writes)
        pass
    elif restricted:
        for rec in self:
            if rec.journal_id in restricted:
                raise ValidationError(_(
                    "You are not allowed to modify entries in journal '%s'."
                ) % rec.journal_id.display_name)
    return res
```

**Why check after super?** Same reason — `journal_id` may have been changed by computed fields or `_onchange` methods before reaching the write.

### Method: `_onchange_journal_id()` (NEW)
```python
@api.onchange('journal_id')
def _onchange_journal_id(self):
    restricted = self.env.user.journal_ids
    if restricted and self.journal_id in restricted:
        self.journal_id = False
        return {
            'warning': {
                'title': _('Restricted Journal'),
                'message': _('The journal "%s" is restricted for you. '
                             'Please select a different journal.')
                        % self.journal_id.name,
            }
        }
```

**Why this UX?** Without this, the user would select a restricted journal, click Save, then get a `ValidationError`. The onchange gives immediate feedback in the UI — better UX.

### Constraint: `_check_journal_not_restricted` (api.constrains)
```python
@api.constrains('journal_id')
def _check_journal_not_restricted(self):
    restricted = self.env.user.journal_ids
    if restricted:
        for rec in self:
            if rec.journal_id in restricted:
                raise ValidationError(_(
                    "Journal '%s' is restricted for the current user."
                ) % rec.journal_id.display_name)
```

**Why a constrains too?** Defense in depth — constrains catches any code path that bypasses `create`/`write` (e.g., direct ORM `_write`, or batch updates via raw SQL would skip constrains but those are admin-only).

## 4. WHY NOT a computed field that raises ValidationError?

The original Cybrosys module had a `_compute_is_check_journal` field that raised `ValidationError` inside a compute method. This is a **known anti-pattern** in Odoo:
- Compute methods are called during read operations (form load, list view, exports).
- Raising `ValidationError` in compute = blocking reads = users cannot even SEE records that have restricted journals.
- This breaks the entire UI — users get error popups when navigating lists.
- Computed fields should be **pure functions**; they must NEVER raise exceptions.

Our design uses `@api.constrains` (called only on create/write) and explicit `create/write` overrides — clean separation of concerns.

## 5. WHY NOT a `models.Constraint` (SQL constraint)?

SQL constraints (`unique()`, `check()`) cannot reference the current user — they run at the DB level with no notion of `self.env.user`. They are unsuitable for user-specific rules.

`@api.constrains` is the correct mechanism — it runs Python code with full access to `self.env.user`.
